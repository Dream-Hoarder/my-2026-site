Understanding Qubes qrexec: Inter-VM Automation

Category: Automation & Systems | Target: Dom0 RPC

In a compartmentalized OS, virtual machines are completely isolated by default. They share no clipboard, no file system, and no networking routes. However, a practical developer environment requires structured data transfer. Qubes handles this securely through its RPC protocol: qrexec.

Rather than utilizing insecure network ports, qrexec allows VM-to-VM commands using the Xen hypervisor vchan channel. The policies governing these interactions are configured inside the admin domain (dom0). Here is how I build secure, automated workflows between restricted security domains.

1. The Anatomy of a Qrexec Policy

All RPC permissions are enforced by dom0 and defined under files in /etc/qubes/policy.d/. A typical policy line consists of: 

# Service-Name + Source + Target + Action
qubes.Filecopy  *  work-dev  vault  ask
qubes.SshAgent  *  work-dev  vault  allow

This policy states that any file copy command executed from the work-dev VM to the offline vault VM must prompt the user via a secure GUI dialogue window, while SSH agent signing requests from work-dev to the vault VM are allowed implicitly without prompts.

Zero-Trust Notice: Never use allow for commands that transmit arbitrary system payloads or access core administrative files. Default to ask or specify specific target VMs.

2. Creating a Custom Telemetry RPC Service

To aggregate logs from my development VMs into a centralized, network-isolated logs VM (sys-log-hub), I configure a custom qrexec service:

Step 1: Define the service configuration in the Target TemplateVM:
Create a script named /etc/qubes-rpc/pp.LogTelemetry inside the template for the log hub: 

#!/bin/sh
# Log ingestion script - Appends input data to a local audit log
read log_payload
echo "$(date -u) [INCOMING] $log_payload" >> /var/log/telemetry/dev-nodes.audit.log

Make the script executable. Since this TemplateVM handles standard RPC invocations, this script is automatically copied to the root directory of the AppVMs spawned from it.

Step 2: Declare the Policy in Dom0:
Inside dom0, create the policy rule file: /etc/qubes/policy.d/30-telemetry.policy: 

pp.LogTelemetry  *  work-dev  sys-log-hub  allow
pp.LogTelemetry  *  @anyvm    sys-log-hub  deny

This policy allows the work-dev VM to transmit text strings directly to sys-log-hub, while denying the privilege to all other untrusted virtual machines.

3. Testing the Automated Pipeline

From inside the work-dev VM, I can now pipe output directly through the qrexec framework using the hypervisor vchan client: 

echo "CRITICAL: Suspicious process spawned in dev environment." | qrexec-client-vm sys-log-hub pp.LogTelemetry

The data bypasses the network stack entirely, traveling directly through hypervisor memory. The log hub processes the payload and appends it to our immutable audit trail, maintaining full operational isolation.
